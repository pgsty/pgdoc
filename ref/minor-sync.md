# 任务流程：小版本增量同步（如 18.6 → 18.7）

上游发布既有大版本的新小版本时，为 `zh/<大版本>/` 做增量更新。**只改英文差异涉及的内容**，未变化的中文原样保留。

## 1. 固定英文源

1. 从官方源码（[FTP 源码目录](https://www.postgresql.org/ftp/source/) 或 Git tag）取得新小版本完整源码，核验 SHA256/提交，确认包内版本声明。
2. 导入 `en/<新小版本>/`（新目录）。已有目录先比对，不静默覆盖本地差异；英文侧若有项目定制与上游内容混杂，分列记录。
3. 记录开工 Git HEAD、`zh/<大版本>/` 工作区状态（含未提交人工修改——中文基线是**当前工作区**，不是旧提交）。
4. 若 `en/` 对应旧小版本树已清理，按 `en/SOURCES.json` 记载或 `.cache/upstream/` 缓存重新取得旧版作对照；新旧两侧必须是各自固定、可追溯的快照。

## 2. 生成完整差异

比较方向统一：**旧 `en/<旧小版本>/` → 新 `en/<新小版本>/`**。

1. 递归覆盖整棵文档源树：顶层、`ref/`、`func/`、图片、实体/包含入口、XSL/CSS、构建脚本。
2. 生成文件（`GENERATED_SGML`）单独分类：用各自版本源码在隔离工作区重建后再比，不混用两侧生成器与输入。
3. 交付：`changes-summary.tsv`（每文件动作/增删行/hunk 数/分类）、`diffs/<相对路径>.diff`、`hunks.tsv`（块 ID、锚点、初步分类）。原始差异完整保留。
4. 差异分类：正文 / 结构（增删改节点）/ 字面示例 / 生成文件 / 构建资源 / 元数据 / 纯排版。

## 3. 组织翻译单元并复用

1. 每个 hunk 形成含完整语境的语义单元；按章节 ID、实体、标题、邻接段落、表格/列表结构定位对应中文，**不按行号硬套**。
2. 跨段落变更形成完整语义单元，限定实际修改范围；纯移动、空白、注释变化不翻译但要有处置记录。
3. 同一英文变更出现在多个适用版本（如 14–18 同步小版本）→ 复用同一译文，保留各版本自己的 SGML 结构、链接与手工格式。
4. 新增段落先检索历史可复用译文（其他版本、发布说明、同族章节）；无基础的才首次翻译。

## 4. 执行翻译

- 遵循 `docs/` 规则与判断顺序（英文语义 → 字面保护 → 词条规则 → 译风）。
- 保留代码、标识符、SGML 结构；上游确实变化的结构/示例随差异同步，保护字面形式不等于保留旧版过时示例。
- 脚本辅助修改：先验证旧文本仍匹配，产生 diff 后逐项审阅。

## 5. 验收

1. 术语、SGML 标签/实体、ID、链接、代码示例、数字与版本条件逐项核对；`git diff --check`。
2. 实际构建 `make -C zh/<大版本> html` 与 `PAPER=A4`/`PAPER=US` PDF；记录命令、退出码、产物路径。
3. 抽查受影响页面（正文、表格、代码、中文字体渲染）。
4. 交付：差异台账（每 hunk 处置）、修改前后对照、构建证据、未决项清单。

## 判例

- **发布说明按英文跨树识别**，不按中文旧文件的标题或位置。
- **版本号、默认值、参数、限制是本版事实**：新版放宽的限制不倒灌旧版；旧版译文忠实于旧版英文不算错。
- **行内 literal 折行**用 `行首锚 + 弹性空白` 的正则定位，单行 grep 会漏折行位点。
- **同一英文多版本复用译文时**，各版链接目标（`linkend`）、ID、包含链保持本版原样。
- **术语邻接空格二阶缺陷**：术语汉化后紧邻的半角空格/标点须一并调整为全角。
